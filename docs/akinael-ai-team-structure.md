# アキナエルAI チーム構成書

作成日: 2026-08-25
位置づけ: アキナエルAIのAIチーム、案件ワークスペース、料金運用、人間承認の責務を一覧化する正式な構成書。

## 1. 全体構成

アキナエルAIは、1つのLLM接続を共通基盤として使用し、用途ごとに役割とワークスペースを分離する。

```text
共通LLM（1接続）
├── 公開窓口・顧客対応領域
│   ├── public_concierge
│   ├── customer_concierge
│   └── admin_commander
├── 案件別の制作ワークスペース
│   └── 制作専門チーム 9役
├── 料金・決済運用領域
│   ├── 料金判定
│   ├── 見積・提案
│   ├── 課金・返金・解約管理
│   └── 承認ゲート
└── 人間の責任領域
    ├── 料金・契約の最終確認
    ├── 外部影響操作の実行承認
    └── 品質・法務・リスクの最終判断
```

AIの役割は、1つのLLMに渡すシステムプロンプト、入力範囲、成果物、権限、前工程依存によって分離する。モデル自体を役割ごとに複数契約する構成ではない。

## 2. 共通LLM基盤

| 項目 | 設定 |
|---|---|
| 接続数 | 1本 |
| 接続方式 | OpenAI互換Chat Completionsアダプター |
| 本番モデル設定 | `gpt-4o-mini` |
| 接続先設定 | `LLM_BASE_URL` |
| 認証情報 | `LLM_API_KEY`。画面や顧客向けAPIには返さない |
| ローカル動作 | APIキー未設定時はモック応答 |
| 共通温度 | `0.2` |

全AIに共通して適用する基本ルール:

- 料金、順位、売上、問い合わせ数、広告成果などを保証しない
- 未確認の情報を断定しない
- 料金・契約・個別見積は正式ルールを参照する
- 相談だけでは契約、申込み、承認とみなさない
- 追加料金が必要な場合は、内容、料金、作業範囲を先に説明する
- 公開、課金、返金、削除などの不可逆操作は人間承認を必須とする
- 顧客にはAPIトークン、モデル使用量、ACなどの内部指標を表示しない

## 3. 公開窓口・顧客対応チーム

### 3.1 `public_concierge`

| 項目 | 内容 |
|---|---|
| 対象 | 未ログインの訪問者 |
| 担当 | サービス、料金、提供範囲、進め方、返金方針の案内 |
| 入力 | 訪問者の質問と直近8件の会話履歴 |
| 制約 | 個別の申込みや詳細相談は会員登録後に案内。会話は保存しない |
| 実装 | `POST /api/public/chat` |

### 3.2 `customer_concierge`

| 項目 | 内容 |
|---|---|
| 対象 | ログイン済み顧客 |
| 担当 | 案件ごとの相談、進捗、制作内容、料金に関する案内 |
| 入力 | 案件名、案件ステータス、直近12件の案件メッセージ |
| 制約 | 顧客の相談を自動的な有料申込みや実行承認として扱わない |
| 実装 | `POST /api/projects/:id/messages` の顧客投稿時に応答 |

### 3.3 `admin_commander`

| 項目 | 内容 |
|---|---|
| 対象 | 管理者 |
| 担当 | 案件の進行相談、料金判断の整理、チームへの指示案作成 |
| 入力 | 案件名、案件ステータス、管理者の指示 |
| 制約 | 公開、課金、返金、データ削除などを直接実行できない |
| 実装 | `POST /api/admin/projects/:id/commander` |

## 4. 案件別制作ワークスペース

顧客案件を作成すると、案件専用のワークスペースIDを発行する。各タスクには `workspaceId`、担当ロール、担当名、目的、成果物、依存先を記録する。他案件のタスクとは混在させない。

### 制作チーム 9役

| 順番 | ロール | 表示名 | 主な責務 | 成果物 | 依存先 |
|---:|---|---|---|---|---|
| 1 | `customer_intake` | 顧客ヒアリングAI | 相談内容、店舗情報、目的、制約を整理 | ヒアリング整理票 | なし |
| 2 | `project_director` | 制作ディレクターAI | 方針、優先順位、受け入れ条件を定義 | 制作方針・受け入れ条件 | 顧客ヒアリング |
| 3 | `research_strategist` | 調査・戦略AI | 顧客、競合、地域性、検索意図を調査 | 改善戦略・調査メモ | 制作ディレクター |
| 4 | `ux_architect` | 情報設計・UX AI | ページ構成、導線、ユーザー体験を設計 | サイトマップ・画面設計 | 調査・戦略 |
| 5 | `content_editor` | コンテンツ編集AI | 紹介文、見出し、FAQ、CTAを作成・校正 | 掲載原稿・FAQ | 情報設計・UX |
| 6 | `visual_designer` | ビジュアルデザインAI | ブランド、レイアウト、配色、画像方針を設計 | デザイン仕様・ビジュアル案 | 情報設計・UX |
| 7 | `frontend_engineer` | 実装AI | 承認済みの設計と原稿をWebページへ実装 | 実装済みHTML・アセット | コンテンツ編集、ビジュアルデザイン |
| 8 | `seo_accessibility` | SEO・アクセシビリティAI | 構造化、検索導線、表示、アクセシビリティを点検 | SEO・アクセシビリティ点検表 | 実装 |
| 9 | `quality_assurance` | 品質保証AI | 要件、文章、デザイン、機能、表示、法務注意点を横断確認 | 品質検査レポート | 実装、SEO・アクセシビリティ |

### 制作ワークフローの実行ルール

- 前工程のタスクが完了しない限り、依存する後工程は実行できない
- `frontend_engineer` はコンテンツ編集とビジュアルデザインの両方が完了するまで待機する
- `quality_assurance` は実装とSEO・アクセシビリティ点検の両方が完了するまで待機する
- 制作AIは担当範囲を越えて契約、課金、公開、広告配信を判断しない
- 品質保証AIは制作担当と別の役割として検査する
- 本番公開は品質確認と人間の公開承認後に実行する

実装箇所: `src/server.mjs` の `PRODUCTION_TEAM`、案件作成、ワークフロー作成、タスク実行ルート。

## 5. 料金・顧客対応に関する専門責務

料金専門の独立モデルは持たず、共通LLMに料金ルールを注入する。料金判断は各AIが独自に作らず、`businessConfig` の正式ルールを参照する。

### 料金運用の論理担当

| 担当 | 責務 |
|---|---|
| 料金判定担当 | 相談内容を「プラン内」「オプション」「上位プラン推奨」「個別見積」に分類 |
| 見積・提案担当 | 現在のプラン内対応、必要な作業、追加料金、提案内容を提示 |
| プラン管理担当 | お試し、本契約ミニ、しっかり運用、発展運用の適用範囲を確認 |
| オプション担当 | Web制作、広告、CMS、予約、CRM、API連携などの単発・特殊作業を整理 |
| 請求運用担当 | 請求額、通貨、決済状態、Checkout、外部費用を管理 |
| 返金・解約担当 | 契約条件に基づく返金・解約の確認と担当者への引き継ぎ |
| 料金品質担当 | 誤案内、無理なアップセル、保証表現、内部指標の露出を確認 |
| エスカレーション担当 | 判断不能、クレーム、法務・権利・高額・高リスク案件を人間へ引き継ぎ |

これらは現時点では料金ルール、顧客対応AI、管理者司令塔、承認APIにより構成される論理的な責務である。`pricing_strategy` などの別エージェントを追加登録した状態ではない。

## 6. 正式料金体系

| 区分 | 料金 | 位置づけ |
|---|---:|---|
| お試し | 0円 | 簡易相談、簡易提案、簡易試作 |
| 本契約ミニ | 月額3,980円 | 日常的な相談、企画、文章、簡易調査、少量画像 |
| しっかり運用 | 月額7,980円 | Web、SNS、SEO、競合、アクセスの継続改善 |

| Webサイト正式制作・公開 | 19,800円〜 | 標準5ページ程度。大規模・特殊機能は別見積 |

## 7. 承認・人間責任チーム

AIが提案や整理を行っても、以下は人間の責任領域とする。

- 料金、契約、返金、解約条件の最終確認
- オプション申込み、プラン変更、有料作業、追加料金への同意確認
- Webサイト本番公開、SNS投稿、メール送信、広告配信
- 広告費変更、外部サービス連携、自動化の有効化
- 顧客データ変更、決済、返金、削除
- 法務、個人情報、権利、重大品質リスクの最終判断

料金への同意と、外部に影響する操作への実行承認は分離する。料金同意があっても、本番公開や広告配信の実行承認にはならない。

## 8. 料金承認の状態と履歴

追加料金やプラン変更が必要と判定された場合、作業を開始せず `PENDING_APPROVAL` とする。

承認成立の例:

- 「その金額でお願いします」
- 「このオプションで進めてください」
- 「発展運用に変更してください」
- 「19,800円でお願いします」
- 「申し込みます」

承認とみなさない例:

- 「いいですね」
- 「なるほど」
- 「考えておきます」
- 「それもありですね」
- 「できるならやりたい」
- 「どんな感じ？」

後から確認できるよう、顧客、案件、提案内容、料金、オプション、プラン変更、承認内容、承認日時、実行日時、実行結果を記録する。

## 9. 顧客案内の原則

- 相談しただけで料金を発生させない
- 顧客向け説明ではAI・人間の内部処理を商品区分に使わない
- 内部のAPI原価、モデル使用量、ACを表示しない
- 無理なアップセルをしない
- 成果、順位、売上、問い合わせ、来店、ROAS、AI検索掲載を保証しない
- プラン外依頼は、まず無料で内容を整理し、見積・提案のみを行う
- 明確な顧客承認前に、プラン変更、追加課金、有料API処理、本制作、広告配信を開始しない
