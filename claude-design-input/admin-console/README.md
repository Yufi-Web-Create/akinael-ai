# Handoff: アキナエルAI 運営者向け管理ツール（新規UI）

## Overview
既存管理画面を置き換える運営者向け管理ツールの新規UI/UX設計。目的は「どの案件で・今何が起きていて・自分が何を判断すべきか」を開いた瞬間に把握できること。Workflow / Task / Artifact / Deployment Gate / Human Gate 等の内部語は通常運用画面から排除し、日本語の業務用語へ翻訳して表示する。

実装先は既存の `admin/`（React + TypeScript + Vite）。

## Fidelity
高精細（hifi）。配色・タイポグラフィ・余白・主要コンポーネント・状態遷移・コピー文言は最終案として扱う。主要ブレークポイントはデスクトップとモバイル390px。中間幅はレスポンシブに最適化してよい。

## IA
1. ホーム
2. 顧客（→顧客詳細）
3. 案件（→案件詳細）
4. AIチャット（案件ごとのスレッド一覧→個別チャット）
5. 制作物
6. 契約・料金
7. 設定（→デザイン・運用ルール／開発者向け情報）

「お客様との相談ログ」は案件詳細・顧客詳細からのみ遷移するサブ画面。

## デザイントークン
Industryデザインシステム準拠。
- 背景 `#f2f2f3`
- サーフェス `#e9e9ea`
- 文字色 `#1d1f20`
- アクセント `#5980a6`
- 見出し `Barlow Condensed`
- 本文 `Barlow`
- このUIは角丸0を基本とする

機能色:
- 完了・正常: green
- 確認が必要: orange
- エラー・緊急: red
- 進行中: accent blue
- 通常: neutral

色だけで状態を伝えず、必ずアイコン・文言を併用する。
主要カードは blueprint風の四隅レジストレーションマークを使用し、影は控えめ。

## 1. ホーム
目的: 今日対応すべきことを一瞬で把握。
- 最大幅920pxのシングルカラム。
- 上部に「対応が必要」ヒーローカード。件数を大きく表示。
- その下にアクションカードを縦積み。
- 下部に統計タイル: 制作中 / お客様確認待ち / 完了 / 新規相談。
- アクションカード例: AI作業提案、顧客からの修正要望、支払い失敗。
- クリックで案件詳細または契約・料金へ遷移。

## 2. 顧客一覧
- 顧客名・店舗名の検索。
- デスクトップはテーブル、モバイルはカードリスト。
- 顧客名/店舗名・契約プラン・案件数・最終更新・状態。
- 状態タグは「契約中」「相談中」等の平易な日本語。

## 3. 顧客詳細
- 店名＋担当者名。
- 基本情報 / 契約の2カラム。
- 紐づく案件カード。
- 「過去の相談を見る」で相談ログへ。

## 4. 案件一覧
- フィルタ: すべて / 判断待ち / 制作中 / お客様確認待ち / 完了 / 新規相談。
- デスクトップはテーブル、モバイルはカード。
- 案件名・顧客・状態・今やること・担当AI・最終更新。
- 内部ステータスコードを表示しない。例 `needs_admin` → 「あなたの判断待ち」。

## 5. 案件詳細
管理ツールの中心画面。
- 案件名、顧客名、状態、最終更新、契約金額。
- クイックリンク: お客様との相談 / 司令塔AIに相談 / 成果物を見る。
- 「今の状況」カードは司令塔AIが自然文で要約し、DB生値を羅列しない。
- 「確定した相談内容」カードはチェックリスト＋金額＋お客様承認済みタグ。

状態別ブロック:
- `needs_admin`: AI作業提案。「承認して進める」「修正を指示」。承認は確認ダイアログ経由。
- `in_progress`: 5ステップ程度の作業状況。
- `needs_customer`: 顧客要望を表示し「司令塔AIに相談する」。
- `done`: 運用状況、公開サイトを見る、次回提案について相談。
- `new`: 相談内容未確定の案内。

## 6. 司令塔AIチャット
- 案件ごとに独立スレッド。
- トップからはスレッド一覧→個別チャット。
- 案件詳細からは該当案件へ直接入る。
- 管理者発言は右、AIは左。
- Enter送信、Shift+Enter改行。
- 案件文脈を必ず保持する。
- productionではモック応答を使わず実Backendへ接続する。

## 7. お客様との相談ログ
- 顧客と相談役AIのやり取りをタイムライン表示。
- 管理者はここで直接返信しない。
- 「この相談についてAIに聞く」で同じ案件の司令塔AIチャットへ文脈を引き継ぐ。

## 8. 制作物
- 案件ごとの成果物をプレビュー中心のカードで表示。
- 状態: AI確認済み / お客様確認待ち / 修正中 / 完成。
- 「プレビューを開く」は実artifact / `preview_url` を使用。
- 状態に応じ「お客様へ確認依頼」「修正を指示」「公開サイトを見る」。

## 9. 承認パターン
「承認」という一語だけでなく結果が分かる文言を使う。
- 制作開始前: 「承認して進める」
- 成果物送付前: 「お客様へ送る」
- 公開前: 「公開する」
- 料金変更: 「料金を変更する」

実行前は共通確認ダイアログ、実行後はトーストで明確にフィードバックする。
Human Gate対象は既存ルールに従う。

## 10. 契約・料金
- 顧客・契約プラン・月額・状態・次回支払・アクション。
- モバイルはカード。
- 決済エラーは赤タグと平易な説明。
- Stripe内部管理画面の露出ではなく、Backendから安全に取得できる情報のみ表示する。

## 11. 設定
- 基本情報
- 通知設定
- 担当者・権限
- デザイン・運用ルール
- 開発者向け情報（最奥）

開発者向け情報にもWorkflow / Task / Artifact等の生の内部語を極力露出せず、通常運用では使用しないことを明示する。

## Interactions
- SPAルーティング相当。selectedCustomerId / selectedProjectId / chatContextProjectId等の文脈を保持。
- 承認ダイアログ後は状態更新＋トースト。
- 顧客検索と案件フィルタは即時反映。
- fadeInUp / popCheck / bounceDot / toastIn 等、控えめなモーションのみ。
- prototypeの表示切替ツールは本番実装しない。

## State Management
- screen
- selectedCustomerId
- selectedProjectId
- chatContextProjectId
- logContextProjectId
- 顧客検索文字列
- 案件ステータスフィルタ
- dialog state
- 案件ごとの状態・要約
- 成果物確認状態
- 案件ごとのAIチャット履歴
- toast state

## 実データ接続
prototypeの顧客・案件・メッセージはモック。productionでは既存 `customers` / `projects` / `requests` / `messages` 等を調査し、UI用adapter/ViewModelで日本語状態へ変換する。

核心要件:
- mock dataをproductionに残さない。
- 内部ステータスやDBテーブル名を画面にそのまま出さない。
- 管理者の判断操作は正規Workflowへ反映する。
- 顧客確認・公開・決済等はHuman Gateを守る。
- 成果物は実artifact / preview_urlへ接続する。
